## F1. Local plan generation cannot succeed. Severity: blocking.

The route attempts local generation with `stream: false` and
`LOCAL_TIMEOUT_MS.coach`, which is 25 seconds.

That timeout was written for the coach, where `stream: true` means the fetch
resolves as soon as headers arrive, so 25s bounds the connection only. With
`stream: false` the fetch does not resolve until the entire response is
generated, so the same 25s now bounds the whole job.

Measured on the founder's M5 Pro against the real schema and a real library:

| Library size | Prompt eval | Generation | Total | Days returned |
|--------------|-------------|------------|-------|---------------|
| 237 exercises | 8,195 tok | 1,666 tok | **80.4s** | 2 of 4 requested |
| 40 exercises | 2,733 tok in 4.6s | 2,641 tok in 89.2s at 29.6 tok/s | **94.6s** | 4 of 4 |

The second row is the important one. With a deliberately tiny library, prompt
evaluation is only 4.6s and **generation alone is 89.2s**, which is three and a
half times the timeout. This is not a prompt-size problem that a smaller
library would fix. A plan is 1,600 to 2,600 output tokens and the machine
produces about 30 per second.

So in practice: every plan generation burns the full 25s on a local attempt
that cannot finish, logs a warning, and falls back to the cloud. The advertised
local support never runs, and the athlete waits 25s longer than necessary.

There is a second-order risk. The route declares `maxDuration = 60`. A wasted
25s plus a real cloud generation of roughly 2,000 output tokens leaves very
little headroom, so on Vercel this can exceed the limit and fail outright.

One thing this did surface in the PR's favour: at the larger prompt size the
local model returned 2 days when 4 were requested, and `parseGeneratedPlan`
correctly rejected it rather than persisting a broken plan. The validation
works.

### Recommended fix

**Make plan generation cloud-only**, rather than raising the timeout.

The reasoning is product, not just plumbing. Cost optimisation should target
calls that happen often: a scan runs every set, a coach message runs several
times a session. A plan is generated roughly once per mesocycle, about every
five weeks. It is the single worst candidate for local inference in the app,
and 90 seconds of spinner is a far worse experience than a few cents.

Concretely, either drop the local branch from `/api/plan`, or give the planner
its own surface in `ai-provider.ts` with `preferredProvider("plan")` defaulting
to cloud and a `LOCAL_TIMEOUT_MS.plan` sized to the measurements above, so it
can only be turned on deliberately in development.

Note this spans an ownership boundary: `ai-provider.ts` is Claude's file and
`api/plan/route.ts` is Terra's.

## F2. The avoid list is not enforced. Severity: medium, and expected.

`avoid` is collected, passed in the prompt with an instruction to respect it,
and stored on the plan. Nothing structurally verifies the generated plan
against it, so an athlete who says "no overhead pressing" can still be handed a
Shoulder Press if the model ignores the instruction.

This is **correct scoping, not a defect**: enforcement belongs to
`plan-validation.ts`, which is step 5 and Claude's, and Terra explicitly left
it alone and said so. Recording it here so it does not get lost, because until
step 5 lands the avoid list is a suggestion to the model rather than a
guarantee to the athlete.

Equipment, by contrast, IS structurally enforced, because
`filterExercisesForEquipment` decides `allowedExerciseIds` before the model
ever sees the library.

## What is good, specifically

Worth naming, because it is the standard the next handoff should meet.

- **`parseGeneratedPlan` is a real trust boundary.** It rejects unknown
  exercise IDs, a day count that disagrees with the intake, a split that
  ignores an explicit request, reversed rep ranges, duplicate exercises inside
  a day, and a deload week outside the mesocycle. Every numeric field is
  bounded. This is the right shape for parsing model output.
- **Prompt rule 3 treats the athlete's free text as data, not instructions.**
  That is prompt-injection hygiene on a field nobody asked it to defend.
- **The landmark contract was honoured.** `canValidate()` gates, `null` targets
  stay null, and the prompt explicitly forbids replacing a null with a
  plausible number. That is golden rule 4 followed without being restated.
- **Honest reporting.** Terra said live generation and Supabase persistence
  were never exercised rather than implying they were. That statement is what
  told me where to point the measurements, and it is why F1 was found before a
  user hit it.

## F3. Local plan generation is non-viable with this model. Severity: informational.

Now that the timeout is correct, the local path can finish. It still cannot
produce a usable plan. Measured against the library the route actually sends,
137 visible exercises with equipment:

| | Result |
|-|--------|
| Wall clock | 114.6s, inside the 180s budget, so the timeout sizing was right |
| Days | 4 of 4 requested |
| Split | correct |
| Exercise IDs | **2 of 20 invented** |
| Verdict | `parseGeneratedPlan` REJECTS it |

The failure mode is UUID copying. The prompt hands a 12B model 137 raw UUIDs
and asks it to reproduce them exactly. It gets most right and fabricates a
couple, and the trust boundary correctly refuses the plan rather than writing
a reference to an exercise that does not exist.

This is the validation layer doing its job, and it is also the strongest
possible argument for the opt-in-only default landed at `9bdbc7e`. Local
planning should be considered unavailable, not merely slow.

**Consequence worth stating plainly: nobody has exercised `/api/plan` end to
end, and with the current local setup nobody can.** The dev environment has an
empty `ANTHROPIC_API_KEY` by design, so the route returns 503 unless
`AI_PLAN_PROVIDER=local` is set, and setting it produces a 502 after almost two
minutes. Exercising the planner needs either a real Anthropic key in
`.env.local` or a preview deployment.

### Design suggestion: stop sending UUIDs

Not a defect, a cheap improvement that helps every model including the cloud
one. 137 UUIDs at 36 characters each is roughly 1,700 tokens of pure
identifier, and it is the part most likely to be reproduced wrong. Sending a
short stable index or slug instead, and mapping back to UUIDs server side after
parsing, would cut prompt cost and remove the hallucination surface entirely.
Worth doing whenever the planner is next touched.

## F4. The route does not retry a rejected plan. Severity: low.

`PLANNER_DESIGN.md` line 72 specifies: "A plan that fails validation is
regenerated once, then surfaced with the specific problem named." The route has
no retry construct. A rejected plan becomes a 502 and the athlete presses the
button again.

That was a fair reading of the brief, which did not restate the requirement.
But F3 shows invented IDs are a real and measured failure mode, so one
automatic regeneration would convert a visible failure into a slightly slower
success a good share of the time. Worth adding when the planner is next opened,
alongside naming the specific problem rather than the generic "could not build
a valid plan".
