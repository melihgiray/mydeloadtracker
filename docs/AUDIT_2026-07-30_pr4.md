## What it gets right

**The severity policy matches the spec.** Errors are things the athlete stated:
an exercise not in the visible library, equipment they do not have, a movement
on their avoid list, a mesocycle with no valid deload week. Warnings are the
low-confidence estimates: per-muscle volume outside the landmark range, and a
session estimated over the requested length. That split is correct, because
blocking a plan on a practitioner-consensus number would claim more certainty
than the data has.

**Errors actually block.** `parseAndValidateCandidate` throws, which triggers
the retry, and only a clean candidate reaches `createPlan`. Warnings reach the
UI in a collapsible panel that says plainly they do not block the plan.

**`canValidate()` is respected.** Muscles with no landmark are skipped rather
than checked against an invented target.

**The avoid matcher's core case works.** Verified against the real 137-exercise
library:

| Restriction | Blocked | Correct? |
|-------------|---------|----------|
| `no overhead pressing` | 8 shoulder presses, NOT Bench Press | yes, this is the F2 case |
| `no deadlifts` | 7 deadlift variants | yes |
| `I hate lunges` | 6, including Bulgarian Split Squat and Step-Up via movement pattern | yes |
| `dips` | Dips and Seated Dip Machine | yes |

The `overhead` synthesis is the clever part: it adds the token when an exercise
is a press AND is shoulder or vertical-push, so "no overhead pressing" catches
Shoulder Press without catching Bench Press. That distinction is the whole
value of the feature and it is right.

## F5. An unmatched avoid term is silently ignored. Severity: high.

This is the finding that matters.

`exerciseConflictsWithAvoid` requires **every** token of a restriction to
appear in an exercise's metadata. It is a conjunctive AND. So any word the
exercise library does not use makes the conjunction unsatisfiable, and the
entire restriction becomes a no-op. Measured, same real library:

| Restriction | Blocks | Same thing, one more word | Blocks |
|-------------|--------|---------------------------|--------|
| `no barbell` | 41 | `no barbell work` | **0** |
| `shoulder` | 17 | `shoulder impingement` | **0** |
| `back` | 26 | `lower back pain` | **0** |
| `overhead press` | 8 | `overhead press aggravates my shoulder` | 1 |
| `deadlift` | 7 | `conventional deadlift` | 1 |

The intake field is free text labelled "Things to avoid". An athlete will write
"lower back pain", not "back". So the natural phrasing is exactly the phrasing
that fails, and only terse keyword input works.

**The failure is silent.** No error, no warning, no `avoid_unmatched` code
exists. The plan validates clean, the UI shows nothing, and the athlete has
every reason to believe the constraint they typed was honoured. That is worse
than not having the feature, because the feature's presence is what creates the
belief.

This is the honest-uncertainty rule from CLAUDE.local.md applied to a
constraint instead of a number. The system does not know whether "shoulder
impingement" was respected. It should say so.

### Fix

Additive, and it does not change any matching behaviour. After the per-exercise
pass, for each restriction that matched zero exercises **anywhere in the
library**, emit a warning:

```
avoid_unmatched: "We could not match 'lower back pain' to anything in the
exercise library, so it was not enforced. Name a lift or a movement instead,
for example 'deadlift' or 'hinge'."
```

A warning rather than an error, deliberately. An unmatched term is not a known
violation, it is an unknown, and blocking generation for anyone who writes
prose would be worse than the current state. The honest word is "not enforced",
not "violated".

Owner: Claude. `plan-validation.ts` is assigned to Claude in the handoff table
and the change is additive, so this lands on main after the merge rather than
as another round trip.

## F6. Partial matching implies coverage it does not have. Severity: medium.

`knee pain` blocks 5 exercises: Leg Extension, Lying Leg Curl, Seated Leg Curl,
Nordic Curl, Hanging Knee Raise. It matched them because their names or
movement patterns contain "knee".

It does not block Squat, any lunge, or Sled Leg Press, which are the movements
most often implicated in knee pain. So the athlete gets a plan where hamstring
curls were removed for their knees and squats were not, which is close to
backwards.

The code comment is honest that this "does not claim to diagnose whether an
arbitrary movement is safe for an injury". The athlete does not read code
comments. They see "conflicts with knee pain" on a leg curl and infer the app
understood.

F5's fix mitigates most of this, because a partially-matched term would at
least not be silently unmatched. The residual issue is that matching *some*
exercises suppresses the unmatched warning while still under-enforcing. Worth
revisiting only if a real user hits it; noted rather than fixed, because any
attempt to map injuries to contraindicated movements is a medical claim this
app should not make.
