## What it actually fixes

`progression.ts` line 114 has always told the athlete, on a deload:

> Deload week, about 15% lighter, keep it at RPE 6 or below, half the sets.
> Recover, then rebuild.

That text predates this work. Meanwhile the Log screen prefilled the plan's
full set count at the plan's RPE target, so the coach promised half the sets at
RPE 6 while the form in front of the athlete said four sets at RPE 8. Step 6
makes the prescription honour the promise the app was already making. That is
a better reason to exist than "add a deload feature".

## No double application, which was the main risk

A deload has three levers and each is applied exactly once:

| Lever | Owner | Applied |
|-------|-------|---------|
| Load, 15% lighter | `progression.ts`, `top.weight * 0.85` | once, in `buildNextSessions` |
| Sets, halved | `plan-session.ts`, `ceil(pe.sets / 2)` | once, from the PLAN's count |
| RPE ceiling of 6 | `plan-session.ts`, `min(rpe_target, 6)` | once |

The set halving reads `pe.sets`, the plan's own prescription, and ignores
`next.target.sets`, which `progression.ts` also halves. So the two halvings
never compound. The code says so in a comment, and the measurement below
confirms it.

**Golden rule 2 holds.** `git diff --name-only ce6fb9e..dfe0d6d` touches no file
under `src/lib/analytics/`. The analytics brain is consumed, never edited.

## Verified in the browser, not asserted

The seeded plan starts 2026-07-29 with a 5 week mesocycle and deload in week 5,
so it was in week 1 and no deload was due. I moved `started_on` back four weeks
on the throwaway seed to land in week 5, checked the screen, and **restored it
to 2026-07-29 afterwards**. No other data was written.

Result at 393x852, signed in as the test account:

| | Before deload | Under deload |
|-|---------------|--------------|
| Squat target | 4 x 5-8 @ RPE 8 | **2 x 5-8 @ RPE 6** |
| Squat prefill | 100 kg | **85 kg**, which is exactly `100 * 0.85` |
| Rows rendered | 4 | 2 |
| Banner | none | "Week 5 is your planned deload…" |
| `scrollWidth` | 393 | 393, no overflow |

Every number in the banner is true: half the sets, 15% lighter, RPE 6. That
matters because a user-facing "15%" that did not match the code would be an
invented number under golden rule 4. It matches.

The trigger is `readinessDeload || scheduledDeload`, and the copy distinguishes
which fired, including the both-agree case. That is the right union: readiness
can pull recovery forward, and the scheduled week stops an accumulation block
running forever when the detector stays quiet.

## Also included: a real bug fix

`hasHistory` previously required `target.weight > 0`, so a bodyweight lift with
zero added weight was classified as having no history and got a blank prefill.
It now counts zero as history when the equipment is bodyweight. Small, correct,
and unrelated to deloads, so it is worth noting rather than leaving buried.

## Found but left alone

- **`plan-session.ts`'s deload note fallback is dead code.** It reads
  `next?.note ?? "Deload week, half the sets and keep every set at RPE 6 or
  below."`, but `progression.ts` always supplies a note on a deload, so the
  fallback never renders. Harmless, and removing it is not worth a commit on
  its own.
- The `bar-scanner.tsx` hook dependency warning, still.

## Process finding, not a code finding

These four commits landed **directly on local main with no pull request and no
push**, which means they bypassed the CI that was added two days earlier
specifically so that claims get checked automatically. I found them only by
running `git status` at the start of this session.

The code is good and this is not an argument against the work. It is an
argument for routing it the same way as PR #3 and PR #4: a branch, a PR, CI
green on the head commit, then merge. That path has now caught a blocking
timeout defect and a silent-constraint defect. Work that skips it is trusted
rather than verified, which is the thing this project keeps deciding not to do.
