## Three defects, none of which any test could have caught

### 1. The 60s function ceiling, hit twice

First two runs returned `504 Vercel Runtime Timeout` at roughly 65s. The
account is on **Hobby, where 60s per function is a hard cap that cannot be
raised**, so generation had to fit rather than the limit moving.

The retry added for F4 was unconditional, and a second attempt started late
guarantees a timeout. It is now gated on remaining wall clock: a retry that
cannot finish is skipped, and the athlete gets the specific reason the first
attempt failed instead of nothing at all.

That change alone converted a mystery 504 into a precise error in 39s, which is
what made the next two defects findable.

### 2. Prose length was failing whole plans

With timeouts gone, the real error appeared: **"Plan notes is too long"**. The
model reliably writes a plan summary past the 500 character cap, so every
candidate was rejected, the retry doubled the work, and the athlete saw a
timeout caused entirely by wordiness.

Strictness should be proportional to consequence. An exercise id that is not in
the library references nothing and must be refused. A wordy summary is
cosmetic. Model-authored notes and day focus are now trimmed on a word
boundary; every structural check still throws.

### 3. The token cap was truncating the plan

Instrumentation added in fix 1 gave the number that settled it:

```
Plan generation attempt 1: 44153ms, 3000 output tokens
```

Two things at once. A single generation took **44 seconds**, so two could never
fit in 60. And output hit **exactly** the 3000 cap I had just lowered it to,
meaning the tool call was truncated mid-structure, which surfaced as "wrong
number of days". Lowering that cap was my own error: a four day plan is
genuinely that large.

Truncation gives a broken plan; a large cap only gives a slow one. So the cap
went back to 4096 and the speed lever moved to the model:
`ANTHROPIC_PLAN_MODEL=claude-haiku-4-5` in production, via a new `PLAN_MODEL`
split out from `COACH_MODEL`.

**44s to 23.4s, and the plan validates.** That fit is the right one on its
merits, not just for speed: plan generation is a constrained structured
extraction sitting behind a trust boundary that rejects anything malformed,
which is exactly where a faster model is safe to use.

## What this says about the tests

Nothing was wrong with them. 187 tests pass, CI is green, typecheck and build
are clean, and not one of these three defects was findable that way. They were
all properties of the whole chain running against real infrastructure: a
platform time limit, a model's actual prose habits, and a model's actual output
size.

The useful rule is that **a test proves a part, a run proves a product**, and
the planner had six parts and no runs.
